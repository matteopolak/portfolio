Jai is Jonathan Blow's programming language. It's been in a closed beta for a while, and people have built real projects with it, but there isn't much tooling around it. There's no first-party language server, formatter or linter, and you can't try it without getting into the beta.

I wanted to build all of that: a compiler that can run real Jai projects, a language server that works in any editor, a formatter, a linter, and a playground that runs everything in the browser. I worked on it from Oct 1 to Oct 10, and you can try the result in the [Jai playground](/playground/jai).

This was right after [Lodestone](/blog/vibecoding-minecraft), my Minecraft rewrite, so I already had a rough idea of how I wanted to run the agents. Most of this post is about that: how I split up the work, how I checked it, and what I spent my own time on.

## Testing against real projects

The first thing I set up was a corpus of open-source Jai projects, pinned to specific commits, that have to compile and run in CI. There were 7 on the first day and 41 by Oct 6.

I think this was the most important decision in the project. If an agent writes both the compiler and its tests, it can get the tests passing without the compiler being very good. Compiling someone else's game engine is much harder to fake. The instruction I gave was that it had to compile all of the open-source libraries we found, and they still had to work in the browser. Every agent was working towards the same goal, and it was one they couldn't change.

## Starting over on day four

The first version was a VM-based compiler split across a lot of crates. By Oct 3 it was around 330k lines of Rust, and it was getting harder to change. So I had it restarted with a new core, `jaic`, that uses one AST for both the compiler and the language server. Hello world ran on it on Oct 4, and the old code was deleted the same day (about 666k lines across two commits).

I was surprised by how much smaller the rewrite was, and asked how it went from 300k lines to 30k. A week later it was about 72k lines and compiled all 41 corpus projects.

If I'd written those 330k lines myself over three days, I probably wouldn't have been willing to delete them. Since the agents wrote them, it was easy to decide to start over once the design was clearly wrong.

## How the work was split up

The main session ran on Opus. It planned the work, reviewed what came back, verified it and merged it, but didn't do much of the implementation itself.

Implementation went to subagents, each with a specific job like a language-spec pass, stdlib coverage, a performance pass, a CI fix or a bug hunt. There were 241 of them over the ten days. Most (191) ran in their own git worktree with their own cargo target directory, because sharing one target directory left stale binaries around.

Anything that was only reading went to Haiku, like checking the community language server's issue tracker for bugs we also had, or going through a big part of the standard library. Sometimes I chained them, for example having Haiku read part of the stdlib and write a spec, then passing that to Sonnet to implement.

I didn't get the models right at first. In the second week some subagents were running on Opus, and they used about 4 billion cached input tokens before I noticed. After that I made it a rule to use Sonnet for subagents and Haiku for read-only work.

## Memory files, docs and checks

With this many agents, anything I only said once in a chat would get lost. So rules went into a few places the agents would always read.

The first was memory files. There were 15 rules by the end, and most came from something going wrong. For example:

- Each agent gets its own cargo target directory.
- Check agent branches before merging them. One agent's commit included the gitignored corpus checkout and wiped it.
- Only one heavy job at a time on my 16 GB Mac. This came after a benchmark used about 84 GB of memory.

The second was docs. I have a global rule that every feature gets a page in `docs/` explaining what it is, how it works and how to change it. That went from 80 pages to 126 during the project, and it meant a new session could work on any part of the code without me explaining it again.

The third was automated checks. `just check` runs the formatter, jailint at deny level and clippy, and there are pre-commit hooks and nine nightly fuzz targets. The formatter and linter also run on the project's own Jai code, which found a lot of bugs early.

## Clean room

Jai's compiler and standard library aren't open source, and this project doesn't copy them. It's built from public information, like the language's documentation and how the open-source projects in the corpus use it. Contributors (including agents) can't read official Jai sources, and that rule is written in the project's public docs.

The standard library follows the same rule. It was written from scratch to support the corpus.

## What I spent my time on

I sent around 870 messages in the main session. Not many of them were asking for a new feature. Most were one of these:

- Setting requirements. The language server had to be a standard LSP server that works in VS Code or Neovim, not something only the playground could use. Errors had to explain what's wrong and suggest a fix where possible. The linter had to actually trace usage instead of matching names.
- Asking for performance with specific targets, like getting debug builds under a second and optimized builds under five, or tracking time, CPU and memory for the language server on a file with 100k+ lines. The agents didn't spend time on performance unless I asked.
- Asking for root-cause fixes. For crashes I asked to fix the underlying issue instead of patching each one, and for an arm64 struct layout bug I asked if we could get rid of that whole class of bugs.
- Saying no to things. There's only one playground (the one on this site), the config stays in TOML instead of switching to another tool's format, and the language server was renamed from `jai-lsp` to `jailsp`.
- Making calls on tradeoffs. Breaking changes were fine if they made things cleaner or faster, since nobody depends on this yet. When a release was missing test coverage, I was fine holding it until the tests were written.
- Using it myself. A couple of the worst bugs happened while all the tests were passing. One agent skipped type-checking some `switch` cases to get code compiling, which broke hover inside those cases. A lint autofix turned `ms[i] - ms[j]` into `it - it`. I found the first one by using the editor and the second by reading a diff. I also found most of the UX issues this way, like Escape closing the whole modal or Tab not accepting completions.

## Takeaways

- Test against real projects that the agents didn't write.
- Have the main session review and merge, let subagents implement, and use cheaper models for reading. Check which model your subagents are actually using.
- Give each agent its own worktree and build directory, and limit how many heavy jobs run at once.
- Write corrections down in memory files or docs so they don't have to be repeated.
- Don't be afraid to restart early if the design is wrong.
- Use the tools yourself, because some bugs only show up that way.

There's still a lot left to do, including code signing, more of the corpus and the rest of the language spec. But it compiles real Jai in the browser now, and the tooling around it is something I'd actually want to use.
